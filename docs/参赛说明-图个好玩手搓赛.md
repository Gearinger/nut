# 此时此地（Nut）——「图个好玩」大地图全员手搓赛 参赛说明

> 作者：宫赫（hermygong）｜腾讯地图
> 形态：Web（PC + 移动浏览器自适应），另有 React Native 移动端同源实现
> 作品类别：LBS + 社交

---

## 一、一句话说明

**给"正好也在现场"的人，一个临时信息板：以地理围栏为唯一通行证、以时间为边界——堵车时问一句前面怎么了、演唱会里找同好、市集上喊一嗓子；人离开这片范围，内容就自动失效。**

不需要加好友，不需要进群，不需要关注。**人在那儿，就能说话。**

---

## 二、怎么用（3 步）

1. **打开链接 → 填个花名就能进**（不用注册、不用邮箱密码），然后允许定位。地图飞到你所在的位置；定位失败会直接告诉你原因（权限被拒 / 无信号 / 超时）并给"重新定位"按钮，不会悄悄把你丢到一个陌生城市。
2. **看附近**：地图上 📝 是别人留下的留言，紫色虚线面是别人划的聊天室范围。点开就能看。
3. **参与**：点 📝 写一条留言（选时效 24h / 7天 / 永久）；点 💬 在图上圈一块地，起个名字，就建好了一个"只在圈内有效"的聊天室。走出这个圈，消息自动置灰、输入框禁用。

**访问链接**：https://nut-here-now.app-tencent.workbuddy.host/

## 三、为什么做这个：附近正在消亡

我们的线上信息流越来越"全球"、越来越"永久"，反而把"身边"弄丢了。

每天我们有大量时间和几百个陌生人**共处同一片物理空间**——同一段堵死的高架、同一个看台、同一个市集棚子、同一场临时活动。这些时刻天然有强烈的交流动机：前方到底怎么回事？有没有人一起拼车？这个摊主收摊了吗？但现实中没有任何工具能让我们说上一句话。能做的只有打开一个全国甚至全球的信息流，看跟你此刻处境毫无关系的内容。

问题不在于没有信息，而在于**信息交换的前置动作太重了**：加好友、进群、关注、等审核。而"同处一个空间"这件事本身，其实已经是最强的相关性证明——它比任何算法推荐都准。

所以「此时此地」只做一件事：**把"在场"变成唯一的准入条件，把"离场"变成内容的自然终点。**

### 三条设计原则

| 原则 | 含义 | 产品化 |
|---|---|---|
| **空间即权限** | 位置本身就是身份，不需要额外认证 | 聊天室 = 地理围栏，围栏内可聊，围栏外只读 |
| **时间即边界** | 信息有寿命，跟场景寿命对齐 | 留言可选 24 小时（快讯）/ 7 天（日常）/ 永久 |
| **离场即失效** | 人走了，内容就该安静下来 | 离开围栏，消息置灰、输入框禁用，可读不可写 |

## 四、为谁解决什么：四个场景

| 场景 | 谁在用 | 说什么 | 为什么要"在场才算" |
|---|---|---|---|
| **堵车** | 同一段拥堵路段的司机 | "前方事故占用两条道，大概 20 分钟""右侧辅路能绕出去" | 路况只在接下来 20 分钟、前后 2 公里内有效；离开这段路，这条信息就是噪音 |
| **演唱会 / 赛事** | 同一场馆、同一看区的人 | "有人一起拼车回去吗""B 口安检人少""内场有没有人掉了个耳机" | 需要确认对方真的在场，否则会被黄牛、外地网友灌满 |
| **线下市集 / 创意园** | 摊主与逛的人 | "今天延长到 21 点""这个摊还剩最后 3 个""明天还来吗" | 只有走到摊位附近的人才需要知道，全城推送没意义 |
| **临时活动 / 快闪** | 活动组织者与参与者 | 集合点变更、临时通知、现场互助 | 活动结束即失效，天然带时间边界，不需要人工清理 |

延伸可覆盖：景区导览互助、社区邻里、商场门店活动、展会现场。

## 五、地图在图面里干了什么（硬要求自检）

**判定标准：去掉地图，这个作品还成立吗？——不成立。**

因为本作品的**准入、可见范围、内容寿命全部由空间决定**。抽掉地图，"围栏"无从划定，"在场"无从判断，整个产品逻辑直接消失。

### 图面构成

| 图层 | 内容 | 随数据变化 |
|---|---|---|
| **底图** | 腾讯地图瓦片，4 种预设风格可实时切换（标准 / 简洁 / 灰色 / 蓝色），最高 z18 | — |
| **留言打点** | 📝 marker，附近未过期的留言一一点在地图上，点击弹窗看作者与正文 | ✅ 有人发就长出来，过期就消失 |
| **围栏面** | 聊天室的地理范围以多边形面渲染（半透明填充 + 虚线描边） | ✅ 有人建聊天室就多一块面，形状由创建者决定 |
| **我的位置** | 我的实时定位 marker | ✅ 跟随定位 |
| **草稿围栏** | 创建聊天室时实时预览的紫色围栏（圆 / 手绘多边形） | ✅ 拖拽即时重绘 |

### 能点、能筛

- **点**：点 marker 看留言内容，点围栏卡片进聊天室
- **筛**：过期留言在查询层就被过滤（`expires_at` 早于当前时间的不返回），不会出现在图上
- **画**：创建聊天室时可在图上**拖拽圆心、拖拽半径手柄**，或**逐点点击手绘多边形**（最多 12 个顶点）

### 四种围栏尺度：把抽象的"附近"翻译成人能懂的单位

| 半径 | 大概是 |
|---|---|
| 100 m | 一栋楼 / 一家店 |
| 300 m（默认） | 一个街区 |
| 1 km | 一个园区 |
| 3 km | 一片城区 |

## 六、技术做法（最小路径 + 一点不偷懒的地方）

| 层 | 选型 |
|---|---|
| 前端 | React 18 + Vite + maplibre-gl + zustand |
| 后端 | Supabase（Postgres + Realtime + Auth + RLS） |
| 底图 | 腾讯地图瓦片，用 maplibre 的 `addProtocol` 自定义 `tmap://` 协议，在前端消化 TMS 行号翻转与子域规则，不需要后端代理 |
| 移动端 | React Native 0.83 + Expo + react-native-maps，与 Web 共享同一套围栏 / 坐标逻辑 |

三个不偷懒的地方：

1. **坐标系**：设备 GPS 给的是 WGS-84，国内底图是 GCJ-02，两者差 300–800 米。库里统一存 WGS-84，渲染前整体转 GCJ-02，用户拖拽 / 点击取到的底图坐标再转回 WGS-84 入库。这一步不做，留言会漂到马路对面。
2. **围栏判定**：数据库只能做经纬度矩形粗筛，真正的"是否在围栏内"必须在端上算——圆形用 Haversine 球面距离，多边形用射线法；多边形还要算质心与外接半径。
3. **测试**：把这些地理规则抽成纯函数并写单测。Web 端 103 个用例（围栏 59 + 坐标 44），全绿。

## 七、用 AI 工具做地图应用的心得与反馈（有价值的部分）

这一节是这次手搓最想留下的东西。**结论先说：最小路径确实成立——调一个底图 + 铺一层自己的数据，一天能出原型。真正难的从来不是渲染，是"数据怎么和空间绑定"这个产品问题，以及地理这块"看起来简单、错了又很难发现"的细节。**

### 1. "不需要懂坐标系"是本次最大的错觉

**现象**：我在武汉，地图却显示我在上海；留言打点全漂到隔壁街区。

**根因**：两个独立问题叠加。

- 定位拿到的坐标是对的，但 `flyTo` 在地图 style 加载完成之前被调用，会被 maplibre **静默丢弃**，地图一直停在初始默认城市（上海）。
- 换上腾讯底图后，WGS-84 坐标直接画在 GCJ-02 底图上，武汉实测偏 586 米。

**反馈建议**：定位"看起来成功但显示错城市"是新手最容易卡死的地方。希望平台/文档把两件事显式提醒：① 定位成功 ≠ 地图会飞过去，要等 `mapload`；② 接国内底图第一步就是确认坐标系，并提供一行能用的转换函数。这两句话能省掉一个下午。

### 2. 地图是状态机，不是组件——AI 在这里最自信也最容易错

AI 写出来的地图代码，语法挑不出毛病，但踩了四个坑，全靠真机验证才发现：

- 切 tab 不调 `map.remove()`，反复挂载会累积 WebGL context，直到**地图黑屏**；
- `flyTo` 早于 style 加载 → 被静默丢弃（同上）；
- 用 `move` 而不是 `moveend` 监听视野，每帧 `setState` 导致整页高频重渲染；
- 拖拽手柄的 effect 依赖里写了中心/半径，拖动过程中 marker 被重建，**手势直接断掉**（正确做法：依赖只留 shape，用 `setLngLat()` 更新位置，拖拽期间不回写）。

**反馈建议**：这类"能跑但会慢慢坏掉"的问题，静态检查查不出来。建议平台提供一份"地图生命周期检查清单"（初始化 / 销毁 / 事件订阅 / 覆盖物回收），让 AI 生成后逐项自查。

### 3. 让 AI 写地理逻辑，要把规则拆成可测试的纯函数

点在多边形内、Haversine 距离、坐标双向转换——这些让 AI 一次写对的概率不到一半，而且**写错了不会报错，只会位置悄悄偏一点**。我们的做法是把它们全抽成纯函数，然后写单测：

- 断言要写"真断言"。早期我写过 `expect(x).toBe(y) || true` 这种假测试，等于没测。
- 不能想当然。我原本断言"GCJ-02 一定把点往南偏"，实测北京是**向北偏 156 米**；原本以为境外不受影响，实测新加坡在矩形境内，偏移 167 米。
- `Number(null) === 0` 是有限数，所以校验坐标必须先排 `null / undefined / ''`，否则空值会被当成有效坐标 (0, 0) 画到几内亚湾。

有了测试，AI 第二轮基本能收敛。**这是我的核心经验：地图代码的正确性不能靠肉眼 review，要靠可执行的几何断言。**

### 4. 产品上最难的不是做出来，是定义"边界"

做的时候反复纠结的问题，比技术难得多：

- 不在围栏内的人，该禁止进入，还是允许只读？我们选了**只读**——因为"看看隔壁街区在聊什么"本身就是吸引力，也是让人想走过去的理由。
- 围栏尺度多大才算"附近"？最后定了 100m / 300m / 1km / 3km 四档，把抽象的"附近"翻译成"一栋楼 / 一个街区 / 一个园区 / 一片城区"，用户一秒就懂。
- 什么时候该让内容消失？给了 24h / 7天 / 永久三档，而不是替用户决定。

**反馈建议**：做 LBS 产品，建议平台能提供"围栏冲突检测""空间密度提示"这类现成能力——当两个人想在同一个位置建围栏时怎么办，是个真问题，不该每个开发者自己造。

### 5. 关于底图与合规

- 腾讯瓦片服务返回 `access-control-allow-origin: *`，浏览器可直连，用前端自定义协议即可消化其私有规则（TMS 行号翻转、`(x + ry) % 4` 子域），**不需要自建代理**，这对小作品非常友好。
- 但要清楚：腾讯返回的是**服务端渲染好的 PNG，不是 MVT 矢量切片**，所以底图样式只能用官方预设的 styleid，无法再自定义道路/水域配色。想要自定义配色的话，需要走 JSAPI GL（矢量）路线。
- 明文 Key 只适用于本地演示，**公网发布必须走代理转发**，把 Key 收在服务端。这条对参赛作品尤其要注意。

## 九、已知的边界（诚实交代）

- 越界目前是"可进但只读"，还没收紧成"禁止进入"，这是产品选择，不是技术限制。
- 围栏冲突检测（两人想在同位置建围栏）、密码准入、信用分体系——PRD 里有设计，本次**刻意没做**，为了守住"空间 + 时间"这个核心闭环。
- 移动端（React Native）代码已完成并用同一套围栏/坐标逻辑，但依赖原生编译，本次参赛以 Web 链接为准。
